1. Motivation & Approach

Why Rewrite in Rust?

  • Memory safety — The JNI layer passes raw pointers between Java and C++. Null dereferences, double-frees, and use-after-free are silent in C++ but caught at compile time in Rust.
  • Unified error handling — Rust's Result type forces every error path to be handled, vs. C++ exceptions that can be missed across JNI boundaries.
  • Panic safety — Unwinding across FFI boundaries is UB in C++. Rust's catch_unwind guarantees panics never escape to the JVM.
  • Modern tooling — Cargo for build, cargo test for testing, cargo clippy for lints, no CMake complexity for the glue layer.

What Stays in C/C++

The rewrite targets the glue code (JNI entry points, parameter parsing, result construction), NOT the search libraries themselves. Faiss and NMSLIB remain as C/C++ libraries accessed via FFI.

Before (all C++):
  Java → JNI (C++) → faiss_wrapper (C++) → libfaiss (C++)

After (Rust glue):
  Java → JNI (Rust) → faiss_wrapper (Rust) → FFI → libfaiss (C++)
                                                         thin unsafe boundary

Methodology: Bun-Style Big-Bang Rewrite

We followed the approach Bun used to port 535k lines of Zig to Rust in 11 days:

  1. Draft everything fast with stubs allowed
  2. Gate what doesn't compile — get to zero errors via #[cfg(any())]
  3. Un-gate one module at a time, fixing errors as you go
  4. Dissolve stubs into real code
  5. Swarm tests to verify equivalence

8. Benchmarks

Result: Rust JNI is faster than C++ JNI across all measured operations. The vector data transfer path (most important for indexing) is 2.4x faster in Rust.

Results: C++ JNI vs Rust JNI

Measured on Apple M1 Pro, Java 21 (Corretto), 1000 iterations after 100 warmup. Same Faiss library underneath — only the JNI glue layer differs.

OperationC++ JNIRust JNISpeedup
initLibrary (no-op JNI overhead) 41.1 ns 32.4 ns 21% faster
storeVectorData (1000 vectors, dim=128) 594.1 µs (862 MB/s) 247.5 µs (2,069 MB/s) 2.4x faster
storeVectorData append (10×100 vectors) 593.3 µs 248.9 µs 2.4x faster
free(0) (null guard fast path) 34.7 ns 31.6 ns 9% faster
isSharedIndexStateRequired(0) 30.6 ns 28.0 ns 9% faster

Why Rust is Faster

  • storeVectorData (2.4x): Rust uses get_float_array_region to copy directly into a pre-allocated Vec<f32>. The C++ version uses GetFloatArrayElements + per-element push_back with more JNI round-trips per vector.
  • JNI overhead (21%): Rust's catch_unwind at the boundary is lighter than C++'s try/catch + exception checking pattern.
  • Lightweight ops (9%): Fewer indirections — Rust calls Faiss directly without going through the JNIUtilInterface virtual dispatch layer.

Note on Compute-Bound Operations

For operations that are dominated by Faiss computation (index creation, query search, training), both implementations call the same underlying libfaiss.a code. The performance difference there is expected to be negligible (<1%) since the JNI boundary cost is amortized over milliseconds of Faiss processing.

9. Why the C++ Shim Cannot Be Eliminated (Research)

Question investigated: Can the 300-line csrc/knn_shim.cpp be replaced with pure Rust code that constructs C++-compatible vtables? This was researched using multi-source adversarial verification (102 agents, 15 sources).

The Problem

Faiss uses C++ abstract classes (faiss::IOReader, faiss::IOWriter, faiss::DistanceComputer) with virtual method dispatch. To provide custom implementations, you must create an object whose memory layout matches what the C++ compiler produces — specifically a valid vtable pointer as the first 8 bytes.

Three Approaches Evaluated

ApproachMechanismVerdict for Faiss
cxx crate (dtolnay) Most mature Rust-C++ interop. Treats C++ types as opaque. Cannot help — intentionally does not support virtual methods, inheritance, or vtable construction (issues #687, #1678)
autocxx (Google) subclass!() macro generates a C++ "peer" object that delegates virtual calls to Rust trait impls Close but blocked — still generates C++ code internally; non-trivial hierarchies don't work (issue #610, open); not thread-safe
Pure Rust vtable (vtable-rs, rust_cpp_oop) Proc macros generate #[repr(C)] structs with manually-constructed vtable pointers Fragile — works for simple cases; deep inheritance layout was refuted in adversarial verification; ABI-specific; no RTTI; v0.1.5 "for game modding"

Applying to Our Interfaces

InterfaceComplexityPure Rust?Risk
faiss::IOReaderSingle-level, 2 virtualsMaybeMedium — untested with Faiss specifically
faiss::IOWriterSingle-level, 2 virtualsMaybeMedium — same
faiss::DistanceComputerAbstract base, multiple virtuals, hot pathNoHigh — complex hierarchy + perf-critical
FaissIndexBQ (custom)Inherits IndexFlat, deep override chainNoHigh — vtable layout unverified for deep inheritance

Decision: Keep the C++ Shim

The 300-line shim is the correct architecture. It represents 0.02% of the Faiss codebase we interact with. The C++ compiler generates correct vtables automatically — no ABI assumptions, no fragile proc macros, no risk of silent vtable mismatch causing segfaults in the hot path.

This matches industry practice: autocxx itself generates equivalent C++ trampolines under the hood. Our hand-written shim is more readable and auditable than what a code generator would produce.

Future: When This Could Change

  • If Faiss ships a C API for IOReader/IOWriter (bypasses vtable entirely)
  • If autocxx fixes hierarchy limitations (issues #610, #1326)
  • If the Rust ecosystem produces a battle-tested C++ vtable generator
  • If we rewrite the Faiss I/O layer in Rust (massive scope creep — not recommended)

12. Build & Run

Prerequisites

# macOS (Apple Silicon)
brew install libomp gcc
export JAVA_HOME=$(/usr/libexec/java_home)

# Build Faiss from source (one-time, ~5 min)
cd jni && mkdir -p build && cd build
cmake .. -DCONFIG_FAISS=ON -DCONFIG_NMSLIB=OFF -DCOMMIT_LIB_PATCHES=false
cmake --build . --parallel 8

Build the Rust Library

cd jni/rust-port/knn-jni-rs

# Static link (production)
KNN_JNI_STATIC=1 cargo build --release

# Dynamic link (development, fast iteration)
KNN_JNI_STUB_LINK=1 cargo build

Run Tests

# With real Faiss (integration tests)
DYLD_LIBRARY_PATH=/opt/homebrew/opt/libomp/lib KNN_JNI_STATIC=1 cargo test

# Quick check (stub libs, pure logic tests only)
DYLD_LIBRARY_PATH=../../build/release KNN_JNI_STUB_LINK=1 cargo test

Use from Java

# The .dylib can be loaded by the JVM the same way the C++ .jnilib is:
System.loadLibrary("knn_jni_rs");
# Exports identical JNI symbols: Java_org_opensearch_knn_jni_FaissService_*
